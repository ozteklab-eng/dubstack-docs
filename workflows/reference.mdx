This page describes the built-in workflows available from the dashboard.

Availability depends on your connected repository, authoring permissions, enabled add-ons, and runtime capabilities.

In this reference, **pull request** means the provider-native review request for the connected Git provider, including GitLab merge requests and Forgejo pull requests.

## Self-updating content workflows

### Update from code changes

Updates content when source code for products, features, or APIs changes.

| Setting | Value |
| --- | --- |
| Triggers | Custom schedule, code change |
| Default schedule | Twice weekly |
| Update modes | Require review, automatically |
| Required capabilities | Docs repository, repository write access, authoring model |
| Required setup | At least one source repository |
| Context repositories | Supported |
| Integrations | Supported |

Use this workflow when product source changes should produce a docs draft. Add selected source repositories as context so the agent can inspect relevant code while it runs.

Scheduled runs read bounded source change context since the previous comparable scheduled run. Code-change runs are queued from validated merged source repository events.

Code-change events are review-event driven. Configure the source repositories that should act as context, then merge a pull request or merge request in that source repository. Direct pushes can still be inspected by a scheduled run, but they do not replace the review-event trigger path.

If the source repository is a monorepo, add a path scope in the workflow configuration so the run focuses on the relevant app, package, or service. When changed-file metadata is available, code-change events outside that path scope are skipped. Path scope does not change the docs repository that receives generated updates.

Supported source repositories can be on a different provider from the docs repository. For example, a GitHub-backed docs site can use a Forgejo code repository as source context while generated documentation changes still open against the GitHub docs repository.

When integrations are selected, the workflow can include bounded context such as Jira issues or Confluence pages. Keep JQL and CQL queries narrow so the run uses the relevant external context without scanning unrelated workspace data.

Before enabling automatic updates, run this workflow in **Require review** mode and confirm:

- the source repository card validates in Git settings
- the workflow has the expected source repository selected
- the path scope excludes unrelated code
- the generated change targets the docs repository, not the source repository
- the provider event is a merged pull request or merge request when using the code-change trigger

### Update from support feedback

Reviews support feedback and opens targeted content updates on a schedule.

| Setting | Value |
| --- | --- |
| Triggers | Custom schedule |
| Default update mode | Require review |
| Required capabilities | Docs repository, repository write access, authoring model, support feedback integration |
| Context repositories | Supported |
| Integrations | Supported |
| Current runner status | Not yet runnable until support-feedback integration collectors are available |

Use this workflow when recurring support conversations reveal missing or outdated documentation.

The workflow is designed to read bounded support-feedback context, identify recurring themes, and open reviewable documentation updates against the connected docs repository. Source repositories can be selected as additional context when support themes need to be tied back to product or API behavior.

The workflow remains visible in the dashboard so teams can see the intended configuration surface, but it cannot be enabled until the deployment has a supported support-feedback connector and runner.

### Repository copy targets

Copies the active docs source into configured repository copy targets on a schedule.

| Setting | Value |
| --- | --- |
| Triggers | Custom schedule |
| Default update mode | Repository copy targets |
| Required capabilities | Docs repository |
| Required setup | At least one repository copy target |
| Context repositories | Not supported |
| Estimated credits | Starts at 35 credits per run; scales with target count and file volume |

Use this workflow when you want a scheduled backup, migration rehearsal, or provider portability check.

This workflow does not continuously mirror repositories. It runs only when the configured schedule fires or when you run it manually from the dashboard. Each run copies the active docs source into the configured copy targets and records the result in workflow history and usage reporting.

Repository copy targets are configured in **Settings > Deployment > Git settings**. They do not become the active deployment source unless you deliberately switch providers from Git settings.

While a repository-copy run is active, the run history shows the current target and file-count checkpoint. Open the run details drawer to see the same progress alongside the eventual per-target result.

The workflow settings drawer lists the current copy targets before you enable the schedule, including provider, repository, branch, and whether the target is scoped to the site or organization.

Repository copies use the saved provider credentials for the active source and each target. Large repositories or self-hosted targets can take longer because the run must read, validate, and write files through the provider APIs. If one target fails because of provider quota, branch protection, token permissions, or network reachability, the run details show that target as failed while leaving the active deployment source unchanged.

## Slack notifications

When Slack is connected, workflows can post run results to selected channels.

Notification modes:

| Mode | Behavior |
| --- | --- |
| All run results | Post when workflow runs complete or fail. |
| Failures only | Post only when a workflow fails. |

Pull-request workflows can also send review reminders and merged pull request updates.

Invite the app to a channel before selecting that channel for workflow notifications.
