Workflow configuration controls when a workflow runs, what context it can read, and how documentation changes are applied.

Open **Automate > Workflows**, choose a workflow, then use the configuration drawer.

## Trigger types

Each workflow exposes only the trigger types it supports.

| Trigger | Behavior |
| --- | --- |
| Content update | Runs after docs content changes are synced from the connected docs repository. |
| Code change | Runs when a selected supported source repository change is merged. |
| Custom schedule | Runs on a recurring schedule. |

For code-change workflows, select the source repositories that should trigger or inform the run.

## Schedules

Scheduled workflows use one of the supported schedule presets:

| Preset | Behavior |
| --- | --- |
| Daily | Queues after the daily interval elapses. |
| Every Monday | Queues at the next Monday UTC boundary after the previous scheduled run. |
| Every Friday | Queues at the next Friday UTC boundary after the previous scheduled run. |
| Twice weekly | Queues at the next Tuesday or Thursday UTC boundary after the previous scheduled run. |

The scheduler scans enabled scheduled workflows and queues due runs within the configured queue-delay window, normally within 10 minutes.

## API-triggered runs

Workflows that use the **Custom schedule** trigger can also be triggered by a trusted backend system through the Admin API.

Use this when your own scheduler, CI pipeline, release tool, or internal platform should decide when the workflow runs.

Admin API-triggered runs still use the workflow's saved configuration:

- update mode
- context repositories
- integration context
- notification settings
- additional instructions
- workflow-specific setup fields

The Admin API does not bypass readiness checks. The workflow must be enabled, use the **Custom schedule** trigger, have repository authoring access, pass setup requirements, and stay within the daily run limit.

See [API keys](/dashboard/api-keys) for key creation, scoping, and trigger examples.

## Update modes

| Mode | Behavior |
| --- | --- |
| Require review | Opens a provider-native review request for review. |
| Automatically | Applies the change directly when the workflow is allowed to write. |

Use **Require review** for production docs unless the workflow is narrow, low risk, and easy to roll back.

## Context repositories

Context repositories let a workflow inspect source code or product repositories in addition to the docs repository.

Use them when documentation changes depend on product implementation details.

Keep context focused:

- select only repositories relevant to the workflow
- prefer the default branch unless the workflow targets a release branch
- avoid adding broad repositories that increase noise and token usage

Context repositories are read-only. The workflow always writes to the connected docs repository.

## Integration context

Supported workflows can use connected integrations.

| Integration | Typical use |
| --- | --- |
| Slack | Read selected channel or thread context and send workflow notifications. |
| Jira | Read bounded issue context from a JQL query and issue limit. |

Integration context is only available when the integration is connected and the workflow supports that context type.

Slack context requires a selected channel. A thread timestamp can narrow the context to one thread.

Jira context requires a JQL query. The workflow reads a bounded number of issues, capped at 10 per run.

## Translation settings

Translation workflows require at least one target language and deployment-level translation routing.

If translation routing is not available for the deployment, the workflow remains visible but blocked with a runner-unavailable message.

## Additional instructions

Some workflows accept optional instructions that are appended to the built-in prompt.

Use instructions to define product-specific rules, terminology, style, target directories, or review expectations. Keep instructions scoped; broad prompts increase cost and make results harder to review.

The **Apply style guide** workflow requires saved style guide instructions before it can be enabled.

## Notifications

When Slack is connected, workflows can send run results to selected channels.

Notification modes:

| Mode | Behavior |
| --- | --- |
| All run results | Notify when runs succeed or fail. |
| Failures only | Notify only when a run fails. |

Pull-request workflows can also send Slack updates when a generated pull request has been waiting for review and when it is merged.

Invite the app to the target channel before selecting it.

## Run now

Use **Run once** to manually enqueue a supported workflow after it is configured and enabled.

The runner checks readiness before starting. If required repository access, model configuration, setup fields, or integration context is missing, the dashboard shows the blocking reason.
