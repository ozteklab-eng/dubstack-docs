Workflows run the dashboard agent from a clear trigger, bounded context, and update mode.

Use them for recurring documentation maintenance and for drafting updates when product code, API behavior, feedback, or assistant conversations show that content needs attention.

## How workflows work

```text
Trigger
-> snapshot repository and integration context
-> run the dashboard agent
-> create a documentation update
-> open a provider-native review request or direct commit
-> record the run and notify Slack if configured
```

The docs repository remains the write source of truth. Workflows write through the connected Git provider, and published docs continue to render from synced artifacts.

## Requirements

Before enabling workflows, connect:

- a Git-backed docs repository
- write access for the docs repository through a supported Git provider
- an authoring model profile

Some workflows require additional signals:

- **Update from code changes** requires at least one selected source repository.
- **Draft improvements from user feedback** requires feedback collection.
- **Draft improvements from assistant conversations** requires assistant analytics.
- **Apply style guide** requires saved style guide instructions.
- **Translate content** appears in the catalog, but it is blocked until translation routing and policy support are available for the deployment.

## Trigger types

Workflows can run from supported trigger types:

| Trigger | Use case |
| --- | --- |
| Content update | Run after docs content changes are synced from the connected docs repository. |
| Code change | Run after a selected supported source repository change is merged. |
| Custom schedule | Run on a recurring schedule such as daily, weekly, or twice weekly. |

Each workflow exposes only the trigger types it can safely support. One workflow run has exactly one trigger source.

## Update modes

| Mode | Behavior |
| --- | --- |
| Require review | Open a pull request or merge request for a teammate to review before merge. |
| Automatically | Apply the update directly when the workflow is allowed to write. |

Use review mode for production docs unless you have a narrow workflow, predictable output, and clear rollback expectations.

## Context

Workflows can read bounded context from:

- the connected docs repository
- selected source repositories
- connected integrations such as Slack or Jira
- published docs, assistant analytics, and feedback signals when the workflow requires them

Context stays scoped to the current organization, deployment, and enabled integration settings. Context repositories are read-only; workflow writes always target the connected docs repository.

## Run lifecycle

Runs are queued and processed by the workflow runner.

| Status | Meaning |
| --- | --- |
| Queued | The run is waiting for a worker. |
| Running | The agent is collecting context and preparing an update. |
| Succeeded | The run completed and recorded a review request or commit result. |
| Failed | The run could not complete. Failed runs do not count toward the daily run limit. |

A workflow can be configured while the runner is disabled, but it only becomes runnable when repository access, model routing, setup requirements, and runner support are all ready.

## Usage limits

Each workflow is limited to 500 queued, running, or succeeded runs per UTC day by default. Failed runs do not count toward that limit.

Runs also record AI usage metadata so credit reporting can attribute cost to the workflow, selected model profile, writer connector, context connectors, trigger type, and update mode.

See [AI credits and usage](/ai/credits-usage) for the shared usage ledger fields and reporting model.
