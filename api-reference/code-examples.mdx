Code examples give readers a copyable starting point for calling each endpoint.

DubStack generates examples from the same request state used by the interactive playground, so the snippets stay aligned with the method, URL, inputs, headers, authorization, and body shown on the page.

## How examples are generated

Generated examples come from the published OpenAPI operation and the current playground inputs.

| Source | Example behavior |
| --- | --- |
| `servers` | Sets the base URL used in snippets. |
| Path parameters | Replaces path placeholders such as `{projectId}`. |
| Query parameters | Adds URL query strings. |
| Header parameters | Adds request headers. |
| Security schemes | Adds the authorization header or field shown in the playground. |
| Request body | Adds a JSON payload when the operation accepts a body. |
| Examples and defaults | Provides safer starting values when the spec includes them. |

When a reader edits a playground input, the generated example updates to match that request.

## Add useful request examples

The best generated examples start with a useful OpenAPI spec.

Add examples to request bodies when an endpoint accepts JSON.

```yaml
paths:
  /v1/projects:
    post:
      summary: Create project
      requestBody:
        required: true
        content:
          application/json:
            schema:
              $ref: '#/components/schemas/CreateProjectRequest'
            examples:
              minimal:
                summary: Minimal project
                value:
                  name: Developer docs
```

Field-level examples are also useful when a full request example is not available.

```yaml
components:
  schemas:
    CreateProjectRequest:
      type: object
      required:
        - name
      properties:
        name:
          type: string
          example: Developer docs
        visibility:
          type: string
          enum:
            - public
            - private
          example: public
```

## Keep examples safe

Use placeholder values for credentials, customer identifiers, and environment-specific data.

```json
{
  "projectId": "proj_123",
  "name": "Developer docs"
}
```

Do not commit real customer data or live credentials to a public OpenAPI file.

## Add endpoint SDK examples

Generated examples are best for direct HTTP requests.

Use `x-codeSamples` on an OpenAPI operation when readers should see SDK, CLI, or workflow examples directly on the generated endpoint page.

```yaml
paths:
  /mcp:
    get:
      summary: Get MCP discovery
      x-codeSamples:
        - lang: bash
          label: Fetch the discovery document
          source: |
            curl --request GET \
              --url https://dubstack-docs-test.dubstack.live/mcp
        - lang: javascript
          label: Load tools from the discovery document
          source: |
            const response = await fetch('https://dubstack-docs-test.dubstack.live/mcp');
            const discovery = await response.json();

            console.log(discovery.capabilities.tools);
```

Each sample supports:

| Field | Required | Purpose |
| --- | --- | --- |
| `lang` | Yes | Syntax highlighting language or alias. |
| `label` | No | Human-readable title for the sample. |
| `source` | Yes | Copyable source code. |

Use endpoint SDK examples when you need to explain:

- SDK usage
- retry behavior
- pagination loops
- webhook verification
- long-running jobs
- error handling patterns

Use regular MDX examples when the content belongs in the surrounding guide instead of the endpoint page.

````mdx
```javascript Node.js SDK
const project = await client.projects.create({
  name: 'Developer docs',
});
```
````

## Troubleshooting snippets

If a generated example looks wrong:

1. Check the operation method and path in the OpenAPI spec.
2. Check `servers` for the correct base URL.
3. Confirm required path and query parameters have descriptions and schemas.
4. Add request body examples for complex payloads.
5. Confirm the endpoint page is mapped to the intended OpenAPI operation.
