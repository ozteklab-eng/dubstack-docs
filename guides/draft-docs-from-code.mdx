title: Draft docs from code changes
description: Connect a source repository, scope the context, and use a workflow to draft documentation updates from product code changes.

Use this guide when product code changes should create reviewable documentation updates.

This pattern keeps two repositories separate:

| Repository role | What it does |
| --- | --- |
| Docs repository | Publishes the live docs site and receives generated documentation changes. |
| Source repository | Provides code or product context for the workflow. |

The source repository does not become the live docs source. The workflow reads bounded context from it, then drafts changes against the connected docs repository.

## When to use this

Use a source repository workflow when:

- API, SDK, UI, or platform code lives outside the docs repository
- a monorepo contains the code that should influence a specific docs area
- engineers merge implementation changes before updating docs
- you want a reviewable pull request or merge request instead of direct docs edits

Use normal docs publishing when the change is already written in the docs repository.

## Requirements

Before configuring the workflow, confirm:

- the site has an active docs repository in [Git settings](/deployment/git-settings)
- repository authoring access is ready for the docs repository
- the source repository is connected in Git settings
- the workflow you want to use supports the **Code change** trigger
- the workspace has enough AI credits and workflow access for the run

For provider-specific setup, see [Git providers](/deployment/forgejo-github-gitlab).

## Connect the source repository

1. Open the dashboard.
2. Select the site.
3. Go to **Settings > Deployment > Git settings**.
4. Add the product or code repository as a source repository.
5. Select the provider, repository, branch, and optional path scope.
6. Save the source repository.
7. Confirm the source repository card shows a valid connection.

For self-hosted providers, the instance must be reachable by dubstack and the token or OAuth connection must have permission to read the selected repository.

## Scope the repository context

For large repositories, add a path scope before enabling the workflow.

Examples:

```text
apps/marketing
services/api
packages/sdk
```

Path scope keeps the workflow focused and reduces irrelevant context.

<Callout type="info">
  Path scope is a context boundary. It does not change where the docs site publishes from, and it does not publish the source repository directly.
</Callout>

## Configure the workflow

1. Open **Automate > Workflows**.
2. Select **Update from code changes**.
3. Choose **Code change** as the trigger when available.
4. Select the connected source repository.
5. Set the update mode to **Require review** for the first rollout.
6. Add any instructions that describe the docs area, terminology, and review expectations.
7. Save the workflow.

Use **Require review** until the workflow has produced several correct drafts. Direct updates should be limited to narrow, low-risk workflows.

## Validate with a small change

Use a small source change for the first test.

1. Open or merge a small pull request or merge request in the source repository.
2. Wait for the provider event to queue the workflow, or run the workflow manually if events are not configured.
3. Open the workflow run details.
4. Confirm the run collected the expected source repository and path scope.
5. Review the generated docs branch or pull request.
6. Merge the docs change only after confirming the content is correct.

The workflow output should land in the docs repository, not the source repository.

## Troubleshooting

### The workflow does not run after code changes

Check:

- the workflow is enabled
- the trigger is set to **Code change**
- the source repository is selected
- the provider event subscription is active where supported
- the changed files match the configured path scope
- the workflow has not hit the daily run limit

If provider events are not available, run the workflow manually to validate source access.

### The workflow cannot read the source repository

Check the source repository card in Git settings.

Common causes are expired tokens, missing repository access, unreachable self-hosted instances, branch renames, or a path scope that does not exist in the selected branch.

### The workflow cannot open a docs pull request

Source repository access is not enough to write documentation changes.

Check that the active docs repository has authoring access, branch creation permission, and pull-request or merge-request permission through the configured Git provider.

### The generated draft is too broad

Tighten the source path scope and add workflow instructions that name the target docs pages, product area, or API surface.
