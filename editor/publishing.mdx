Publishing moves source changes into the public docs runtime.

The exact flow depends on your connected source, selected branch, repository permissions, and branch protection rules. The contract is consistent: source changes are written to Git, synced into published artifacts, and then served by the live site.

```text
Editor or Git change
-> branch, commit, or pull request
-> deployment branch
-> sync job
-> published docs site
```

## Save, publish, and sync

| Stage | What it means |
| --- | --- |
| Edit | Change content, navigation, assets, or site configuration in the dashboard editor |
| Save | Persist the change in the editor or connected source path, depending on the source type |
| Publish | Commit the change, create a branch or pull request, or update the deployment branch depending on repository rules |
| Sync | Build published artifacts from the configured source |
| Live | Serve the updated docs from the public site |

A dashboard preview is useful while editing, but the live site is the final verification target.

## Publish menu states

Click **Publish** in the editor toolbar to inspect the current publish state.

| State | What the menu shows |
| --- | --- |
| No pending changes | The target site, `0 file changes`, and **No pending changes**. |
| Pending changes | The changed-file count, an **Undo all changes** action, and each changed source file with its status. |
| Changed file selected | A diff view for that file, including added and removed line counts. |

Use the changed-file list before publishing to confirm that the edit only touches the expected pages, media assets, snippets, OpenAPI specs, or `dubstack.json` settings.

If a pending edit is wrong, use **Undo all changes** or revert the individual file before publishing. Reopen the editor page after undoing a temporary edit to confirm the source content is clean.

For branch creation, pull requests, merge requests, and review flows, see [Branching and publishing](/editor/branching-and-publishing).

## Source-backed publishing

Use this flow when your site is connected to a customer-owned Git repository.

<Steps>
  <Step title="Choose the working branch">
    Use the branch selector in the editor toolbar or your Git provider to choose where the change should be made.

    Use the deployment branch for small direct edits when your repository allows direct publishing. Use a feature branch when the change needs review.
  </Step>

  <Step title="Make the change">
    Edit pages, navigation, site configuration, assets, or OpenAPI specs.

    For source changes made outside the dashboard, commit and push them to the configured branch. See [Local Git workflow](/deployment/local-git-workflow) for the command-line path.
  </Step>

  <Step title="Review the diff">
    Before publishing, review changed files and confirm the change is limited to the intended pages and configuration.

    Check `dubstack.json` carefully when navigation, theme, redirects, SEO, or API reference settings change.
  </Step>

  <Step title="Publish or open a pull request">
    If the deployment branch allows direct publishing, publish to commit and sync the change.

    If the branch is protected or the change needs review, create a pull request from the feature branch into the deployment branch.
  </Step>

  <Step title="Review the preview">
    Open the preview deployment for the branch or pull request.

    Check page rendering, navigation, search, API reference pages, assistant responses, and any changed assets.
  </Step>

  <Step title="Merge and verify live">
    Merge the reviewed pull request into the deployment branch.

    After the sync finishes, open the live site and verify the updated page directly.
  </Step>
</Steps>

## Hosted repository publishing

Use this flow when the site was created with the hosted starter source during onboarding.

<Steps>
  <Step title="Edit in the dashboard">
    Open the editor and make the content or configuration change.
  </Step>

  <Step title="Save the change">
    Save through the dashboard flow and wait for the activity item to complete.
  </Step>

  <Step title="Verify the published site">
    Open the live URL and confirm the page, navigation, search result, or API reference output changed as expected.
  </Step>
</Steps>

You can move from a hosted source to a customer-owned Git repository later. See [Git essentials](/editor/git-essentials) and [GitHub](/deployment/github).

## Publish from local Git

Developers can publish without opening the dashboard editor.

```bash
git pull
git add .
git commit -m "docs: describe the change"
git push
```

Push directly only when your repository policy allows it and the target branch is the configured deployment branch. Otherwise, push to a feature branch and open a pull request or merge request.

After the push or merge, dubstack syncs the configured source into published artifacts. If the webhook does not arrive, run a manual update from the dashboard.

## Preview deployments

Preview deployments let reviewers inspect a branch before it becomes live.

Use previews to check:

- new pages and deleted pages
- navigation changes
- API reference endpoint rendering
- code blocks, callouts, tabs, accordions, and tables
- custom domain or `/docs` path behavior when relevant
- assistant answers and public MCP discovery after source updates

Preview URLs are temporary review surfaces. The deployment branch remains the source for the production docs site.

For the full branch review workflow, see [Branching and publishing](/editor/branching-and-publishing).

## Manual update

Use manual update when:

- A webhook did not arrive.
- A provider maintenance window delayed repository events.
- You changed a hosted OpenAPI spec URL.
- You need to re-sync the current branch after a failed deployment.
- Support asks you to refresh published artifacts.

Manual update does not replace source control. It re-runs the publish path from the configured source.

## Deployment checks

After publishing, check:

- The activity item finished successfully.
- Deployment history shows the expected latest sync.
- Changed pages open on the live site.
- Navigation and search include new pages.
- API endpoint pages render if the change involved OpenAPI.
- `llms.txt`, `llms-full.txt`, `skill.md`, and public MCP reflect the change when AI discovery is enabled.

<Callout type="warning">
  Do not rely on dashboard preview alone for production verification. Always open the live URL after the publish finishes.
</Callout>

## Troubleshooting

### Publish is disabled

Check that there are pending changes, that your account can write to the source, and that the selected branch allows the action you are trying to perform.

### A pull request is required

Your deployment branch is protected. Create a branch and pull request, then merge after review.

### The live site still shows the old content

Check deployment history. If no sync ran, use manual update and confirm the provider webhook is still configured.

### The preview works but the live site does not

Confirm the pull request was merged into the deployment branch configured in Git settings.

### A generated API page is missing

Confirm the OpenAPI spec path is configured, committed to the source, and included in the branch that triggered the sync.
