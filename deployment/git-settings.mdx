---
title: Git settings
description: Configure the repository, branch, provider access, and authoring connections used by a dubstack site.
---

Git settings control where a site reads documentation from and which Git provider actions are available for publishing, previews, editor saves, agents, and workflows.

Open **Settings > Deployment > Git settings** from the dashboard.

## What Git settings controls

Git settings has five separate jobs:

| Job | What it controls |
| --- | --- |
| Deployment source | The repository, branch, and optional docs directory used to publish the live docs site. |
| Provider access | The GitHub App, GitLab token, or Forgejo token that lets dubstack read source files and receive repository events where the provider supports them. |
| Authoring access | OAuth or app permissions that let approved agents, Slack requests, editor saves, and workflows create reviewable documentation changes. |
| Source repositories | Additional code or product repositories that workflows can read as bounded context. |
| Copy targets | Secondary repositories used for migration, backup, or provider evaluation. |

Keep these jobs separate when troubleshooting. A site can read from a repository while authoring is blocked, and an OAuth connection can be healthy while the deployment source still points somewhere else.

<Callout type="info">
  The docs repository remains the source of truth. Dashboard publishing, agents, Slack, and workflows write through the configured Git provider instead of bypassing repository review.
</Callout>

## Active deployment source

The active source card shows the repository that publishes the site.

Check these fields before debugging content updates:

- provider
- organization or namespace
- repository or project
- branch
- docs directory, if docs are in a subdirectory
- last sync time
- latest manual update result

If the wrong branch is selected, pushes to the expected branch will not update the live docs site.

## Provider picker

Use the Git provider picker to choose the provider you want to configure.

Changing the visible provider does not automatically migrate production traffic. Save and validate the source before treating a new provider as active.

| Provider | Typical use |
| --- | --- |
| GitHub | Primary repository source with GitHub App access, preview deployments, editor commits, and pull-request authoring. |
| GitLab | Repository copy target, GitLab-backed source where enabled, and merge-request authoring through GitLab OAuth. |
| Self-hosted GitLab | OAuth authoring against a reachable self-hosted GitLab instance after the workspace is configured. |
| Forgejo | Self-hosted workflow source repository, repository copy target, and active deployment source where enabled. |

For self-hosted providers, the instance must be reachable from dubstack and the configured token must have the repository permissions needed for the selected workflow.

When you explicitly switch the active deployment source to another enabled provider while another provider is already active, dubstack copies the current docs source into the new repository before the switch completes. If that initial copy fails, the existing active source remains in place and the dashboard shows the copy error. If you only configure a copy target, production stays on the current active source.

## Provider capability matrix

Provider support is capability-based. A provider can be usable for one job while another job is still unavailable or gated.

| Provider | Deployment source | Authoring | Source repository context | Repository copy target |
| --- | --- | --- | --- | --- |
| GitHub | Supported through the GitHub App | Supported through the GitHub App | Supported for selected repositories with app access | Supported where a copy target is configured |
| GitLab | Supported where GitLab deployment source is enabled | Supported through GitLab OAuth | Supported for selected projects when GitLab access is healthy | Supported through a repository access token |
| Self-hosted GitLab | Supported where the instance is reachable and GitLab deployment source is enabled | Supported through self-hosted GitLab OAuth | Supported when the instance and selected projects are reachable | Supported through a repository access token |
| Forgejo | Feature-gated | Supported through a repository token where enabled | Supported for selected repositories and webhook-capable instances | Supported through a repository token |

Use the labels in the dashboard to confirm the active job. For example, a provider marked **Copy target** is not publishing the live site, and a provider marked **Source repository** is read-only context for workflows.

## Read the status labels

A site can have more than one provider connection, but only one provider is the active deployment source.

Use the status labels to identify which path a connection belongs to:

| Status label | What it means |
| --- | --- |
| Active | This provider is the deployment source that publishes the live docs site. |
| Installed | The provider app or OAuth grant is connected for the listed account or organization. |
| Needs reconnect | An authoring grant, OAuth token, or provider-side permission needs to be refreshed before authoring actions can use it. |
| Copy target | The repository can receive an explicit copy from the active docs source for backup, provider testing, or migration rehearsal. |
| Source repository | The repository can be selected as read-only context for workflows such as code-change documentation updates. |
| Webhook configured | dubstack has configured the provider event subscription for the source repository. Verify delivery in workflow run history after a supported review event. |
| Webhook pending | The repository remains usable as scheduled or manual context, but event-driven workflow runs need the webhook path fixed. |
| Configured | The repository or connection has saved settings, but it might not be the active deployment source. |

These labels are intentionally independent. For example, a GitHub repository can remain **Active** for publishing while a GitLab copy target is configured and a GitLab OAuth account shows **Needs reconnect**. In that state, pushes to GitHub still publish the site, the GitLab repository copy can still be valid if its repository token is healthy, and only GitLab authoring actions need the OAuth reconnect.

<Callout type="info">
  Treat **Active deployment source**, **authoring access**, **source repository**, and **copy target** as separate jobs. Fix the job that is failing instead of rotating every provider credential.
</Callout>

## GitHub setup

GitHub source sync uses the dubstack GitHub App.

Use the GitHub App section to:

- install the app into an organization
- grant repository access
- open provider-side installation settings
- verify which organizations and repositories are installed

Grant access only to the docs repository and any repositories intentionally used as agent or workflow context.

<Callout type="warning">
  Do not use personal access tokens for GitHub deployment source sync. GitHub source sync should use the GitHub App installation so repository access, events, and pull-request actions remain auditable.
</Callout>

See [GitHub](/deployment/github) for the full setup and permission model.

## GitLab setup

GitLab has two connections that serve different purposes.

| Connection | Purpose |
| --- | --- |
| GitLab deployment token | Reads or copies repository content, validates branches, and supports GitLab source configuration where enabled. |
| GitLab OAuth | Lets agents and workflows act as an authorized GitLab user to create branches, commits, and merge requests. |

Use the GitLab deployment settings when you need to configure the project, branch, token, or instance URL.

Use the GitLab OAuth section when workflows, Slack, or the dashboard agent need to create GitLab merge requests or use selected GitLab projects as repository context.

If GitLab is configured only as a copy target, pushes to GitLab do not publish the live site. The active deployment source still controls production publishing.

See [GitLab](/deployment/gitlab) and [Self-hosted GitLab OAuth](/deployment/gitlab-self-hosted-oauth) for setup details.

## Forgejo setup

Forgejo setup uses a Forgejo instance URL and repository token.

Use Forgejo when your team runs a self-hosted Forgejo instance and wants to use it for workflow source context, repository-copy targets, or an active deployment source where that mode is enabled.

1. Open the Git provider picker.
2. Choose Forgejo.
3. Enter the Forgejo instance URL.
4. Enter the repository owner, repository name, branch, and optional docs directory.
5. Enter a token that can read the repository and write branches or pull requests when authoring is enabled.
6. Save the connection.
7. Confirm whether the dashboard shows Forgejo as a repository copy target or as the active deployment source.

Forgejo works best when the instance is available over HTTPS and can send provider events to the configured endpoint.

If Forgejo is configured as a repository copy target, it receives explicit repository copies from the active docs source. It does not publish the live site and pushes to Forgejo do not update production docs.

If Forgejo active deployment-source mode is enabled for the workspace, save the Forgejo connection, run a manual update, and confirm the active deployment source card shows the expected Forgejo repository. Do not tell teammates to push docs changes to Forgejo until the active deployment source card confirms Forgejo is serving the site.

### Reuse Forgejo access for workflow source repositories

If the active deployment source already uses Forgejo, source repositories for workflows can reuse the same Forgejo access when they are on the same instance.

Use this when the docs repository and product code repository live on the same Forgejo server and the existing token has permission to read the source repository.

When adding a Forgejo source repository:

- keep the instance URL the same as the active Forgejo deployment source
- enter the owner, repository, and branch for the source repository
- leave the token blank only when the active Forgejo token can read that repository
- save the source repository and confirm the dashboard validates it

If validation fails, provide a repository-specific token with the required read access, or update the active Forgejo token so it can read both repositories.

<Callout type="warning">
  One-time repository copy targets are not automatic mirrors. Use copy targets for migration, backup checks, or provider evaluation, then keep one active production source.
</Callout>

## Docs in a subdirectory

Enable **Docs are in a subdirectory** when `dubstack.json` is not at the repository root.

Example:

```text
product-repo/
|-- apps/
|-- packages/
`-- docs/
    |-- dubstack.json
    |-- index.mdx
    `-- quickstart.mdx
```

Set the docs directory to `docs` for that structure.

Do not include a leading or trailing slash. The path should be relative to the repository root.

For monorepo guidance, see [Monorepo setup](/deployment/monorepo).

## Manual update

Use manual update when you want to re-read the active source without waiting for another Git provider event.

Manual update is useful after:

- changing the repository, branch, or docs directory
- granting repository access to the GitHub App
- rotating a GitLab token
- rotating a Forgejo token
- fixing a webhook delivery issue
- importing or copying docs between providers

After the update finishes, confirm the public site and MCP/search surfaces reflect the latest content.

See [Manual updates and history](/deployment/manual-updates-history).

## Authoring readiness

Authoring readiness is separate from source readability.

Agent, Slack, editor, and workflow authoring can require:

- repository write access through the configured provider
- permission to create branches
- permission to open pull requests or merge requests
- branch protection that allows reviewable changes
- OAuth authoring access where the provider requires a user grant
- workflow eligibility for the current site

If authoring is blocked, keep the live deployment source intact and fix the missing authoring permission shown by the readiness panel.

Provider-native review requests use provider-specific names. GitHub and Forgejo use pull requests; GitLab uses merge requests. In dashboard workflow settings, **Require review** means dubstack should create that provider-native review request instead of committing directly.

Automatic updates require the target branch to allow the connected provider identity to write. If repository policy blocks direct commits, keep workflows in **Require review** mode and merge the generated review request after approval.

## Source repositories for workflows

Workflow source repositories are read-only context repositories selected by workflows such as **Update from code changes**.

They are separate from the active deployment source:

- the active deployment source publishes the live docs site
- source repositories provide code or product context for workflow runs
- generated documentation changes still target the docs repository
- code-change runs are queued from validated merged pull request or merge request events where the provider integration supports them

Use source repositories when the product code and docs live in different repositories, or when you want a workflow to watch a code repository without making that repository the docs source of truth.

Example setup:

| Role | Example |
| --- | --- |
| Active deployment source | `acme/docs` publishes the docs site. |
| Source repository | `acme/api` provides source context for code-change workflows. |
| Workflow write target | Generated updates open a pull request or merge request against `acme/docs`. |

This lets developers keep normal code workflows in the product repository while documentation updates remain reviewable in the docs repository.

The source repository card shows operational metadata for each connected context repository.

| Field | Meaning |
| --- | --- |
| Scope | Whether the source repository is connected for the current site or broader workspace context. |
| Events | Which provider events can queue workflow runs, such as pull requests or merge requests. |
| Configured | When dubstack last configured or refreshed the source repository event subscription. |
| Last delivery | The most recent signed provider event received by dubstack for that source repository. |

If the card shows **Webhook configured**, dubstack has saved the provider event subscription. **Last delivery** confirms whether an event has actually reached dubstack. Confirm workflow behavior by merging a small review event and checking workflow run history. If the card shows **Webhook pending**, **No events received**, or the connection reports a webhook setup warning, the repository is still connected as read-only workflow context, but event-driven runs need the webhook path fixed before merged review events can queue runs automatically.

### Forgejo source repositories

Forgejo source repositories use the same instance URL model as Forgejo deployment sources.

Use Forgejo source repositories when:

- the docs repository is on another provider, but the code repository is hosted in Forgejo
- the docs and code repositories are on the same Forgejo instance
- you want **Update from code changes** to inspect a self-hosted code repository without moving the docs source

When adding a Forgejo source repository, provide:

- instance URL
- owner
- repository
- branch
- a token with read access to the source repository, unless existing Forgejo access can read it

If the source card shows **Webhook configured**, merged pull request events should be able to queue code-change workflow runs. Use **Last delivery** to confirm that Forgejo can reach dubstack, then use run history as the source of truth for whether the event matched a workflow. If event support is unavailable, pending, or blocked by your network, keep the repository selected and use scheduled or manual workflow runs after the source change is merged.

### Path-scoped source context

For large repositories, set an optional path scope in the workflow configuration after the source repository is connected.

The path scope must be a relative repository path, such as:

```text
apps/web
services/api
packages/sdk
```

Do not include a leading slash, `..`, or a full URL.

Path scope tells the workflow which part of the repository is relevant to the docs task. The workflow still writes generated documentation changes to the connected docs repository, not to the source repository.

<Callout type="info">
  When a provider event includes changed-file metadata, code-change workflows skip events that do not touch the configured path scope. If the provider event does not include changed paths, the workflow falls back to repository-level matching and still uses the path scope to bound run context.
</Callout>

## Repository copy targets

A copy target is a secondary repository used for backup, migration, or provider evaluation.

Copy targets are not the same as the active deployment source.

Use a copy target when you want to:

- keep a backup in another Git provider
- test a provider migration before switching production
- validate GitLab or Forgejo flows without disrupting a GitHub-backed site
- preserve a clean escape path if a provider changes terms or availability

Before switching production to a copy target, confirm the target repository has `dubstack.json`, all MDX pages, assets, OpenAPI specs, and a valid deployment branch.

Repository copy targets support explicit one-time copies from Git settings and scheduled copies through the **Copy repository targets** workflow. A successful copy proves that dubstack can read the active source and write to the target provider, but it does not create continuous mirroring, provider failover, or webhook replication.

One-time repository copies do not consume AI credits when they only copy files. Scheduled repository-copy workflows consume automation credits because they are workflow runs, and their results appear in workflow history and usage reporting. Scheduled repository-copy workflows start at 35+ credits per run; final credits scale by copy target count and file volume.

Forgejo copy targets may take longer than GitHub or GitLab targets for large repositories because dubstack writes files through Forgejo's repository content API in sequence. This keeps the target branch consistent while the copy runs.

Provider switching uses the same copy pipeline. A failed copy blocks the switch so the live site keeps publishing from the previous active source.

Use the active deployment source card to confirm what is serving production before telling teammates to push to a different repository.

## Protected deployments

Some deployments are intentionally protected from repository mutation.

Protected deployments can still be read and indexed, but authoring actions should not create branches, commits, pull requests, or merge requests from Slack, agents, or workflows.

Use disposable test deployments for authoring smoke tests.

## Troubleshooting

### Repository list is empty

Check that the provider account is connected and that the app or token has access to the repository owner.

For GitHub, open the app installation and confirm the repository is selected.

For GitLab, confirm the token can read the project and the project ID or path is correct.

For Forgejo, confirm the instance URL is reachable from dubstack and the token can read the selected repository.

### Branch list is missing the expected branch

Confirm the provider credential can read branches and that the branch exists in the selected repository.

If the branch was just created, revalidate Git settings or run a manual update.

### Live docs do not update after a push

Check that the push went to the active deployment branch. Then check provider event delivery and run a manual update.

If manual update works but automatic sync does not, the provider event or webhook path needs attention.

### Source repository shows webhook pending

The repository can still be used as workflow context when the saved credential is valid.

Webhook pending means dubstack could not confirm the provider event subscription for that source repository. For Forgejo, check that:

- the instance is reachable from dubstack over HTTPS
- the repository token can manage webhooks for that repository
- the dashboard did not show a webhook setup warning when the source repository was saved

After fixing the provider or network setting, save the source repository again to refresh the webhook configuration.

### Source repository shows no event deliveries

The webhook may be configured, but the provider has not delivered an event to dubstack yet.

Check that:

- the source provider can reach the webhook URL over HTTPS
- the provider webhook is active and subscribed to pull request or merge request events
- the provider-side delivery history shows a recent success
- the change was merged through a review event, not only pushed directly

If delivery is blocked by your network, use a scheduled or manual workflow run after the source change is merged.

### Agent or workflow cannot create a pull request

Check authoring readiness, not only source sync.

For GitHub, verify the GitHub App has write and pull request permissions for the repository.

For GitLab, verify OAuth is connected, the selected project is enabled for workflow context, and the connected user can create branches and merge requests.

For Forgejo, verify the repository token can create branches and pull requests on the selected repository.

### GitLab OAuth is connected but production still reads GitHub

This is expected when GitHub remains the active deployment source. GitLab OAuth enables authoring/context capabilities. It does not automatically switch production publishing to GitLab.

### A source repository webhook is configured but the live site did not change

This is expected. Source repository webhooks queue eligible workflows and provide context. They do not publish docs content directly. Check the workflow run, review the generated branch or pull request, and merge the change into the active docs repository before expecting the public site to change.
