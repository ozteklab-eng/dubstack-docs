Git is the write source of truth for dubstack docs.

A connected provider lets dubstack read source content, receive update signals, and write documentation changes when an authorized workflow or agent action requires it.

## Provider support

| Provider | Current role |
| --- | --- |
| GitHub | Primary connected-source provider for production docs, previews, editor commits, and agent draft pull requests. |
| GitLab | Connected-source provider, copy target, OAuth authoring integration, GitLab-aware workflows, and merge-request authoring. |
| Forgejo | Self-hosted source provider, copy target, and reviewable authoring path for teams that host docs in Forgejo. |

Provider availability can depend on your plan, workspace configuration, and rollout state.

## Choose a provider path

| Goal | Recommended path |
| --- | --- |
| Production docs from your own repository | [GitHub](/deployment/github) |
| Keep a GitLab copy or prepare a migration | [GitLab](/deployment/gitlab) |
| Draft GitLab merge requests from agents or workflows | [GitLab](/deployment/gitlab) with OAuth authoring access |
| Publish from a self-hosted Forgejo repository | Configure Forgejo in [Git settings](/deployment/git-settings) |
| Review generic provider concepts | This page |
| Configure an unsupported custom provider | Contact support or your dubstack operator before relying on it for production publishing. |

## Connect a repository

From the dashboard:

1. Open **Settings > Deployment > Git settings**.
2. Choose the provider.
3. Authorize the provider app, repository access token, or OAuth flow required by that provider.
4. Select the repository and branch.
5. Save the connection.
6. Run a manual update to verify the first sync.

## Repository requirements

A docs repository should include:

- MDX pages.
- `dubstack.json`.
- Images and assets referenced by pages.
- OpenAPI specs if the site has an API reference.
- Any reusable snippets used by pages.

## Branches and previews

Use the deployment branch for production docs. Use preview branches for review workflows when your plan and provider integration support previews.

Do not use preview branches as the long-term production source.

## Provider permissions

Grant the smallest provider scope that supports your intended workflow:

| Workflow | Permission needed |
| --- | --- |
| Read and publish docs | Repository read access. |
| Dashboard edits | Write access to content files and configuration. |
| Agent draft PRs | Branch and pull request creation access. |
| Webhook-driven updates | Webhook delivery from the provider. |

For GitLab, repository read/copy access and authoring access are separate. The repository access token keeps the GitLab repository connection readable. GitLab OAuth authoring access lets workflows create branches, commits, and merge requests as an authorized GitLab user.

For Forgejo, the repository token must cover the source repository and the actions you want dubstack to perform. Read-only tokens can publish existing content. Authoring workflows need permission to create branches and pull requests.

## First-sync troubleshooting

If the first sync fails:

- Confirm the repository is installed or authorized for the provider app.
- Confirm the selected branch exists.
- Confirm `dubstack.json` is present at the repository root.
- Confirm page slugs in navigation map to files.
- Re-run manual update after fixing provider access.

<Callout type="info">
  You can migrate between provider-backed sources, but keep one active production source at a time to avoid branch and publish confusion.
</Callout>
