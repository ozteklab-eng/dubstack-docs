Git is the write source of truth for dubstack docs.

A connected provider lets dubstack read source content, receive update signals, and write documentation changes when an authorized workflow or agent action requires it.

## Provider support

| Provider | Current role |
| --- | --- |
| GitHub | Primary active deployment source for production docs, previews, editor commits, and agent draft pull requests. |
| GitLab | Copy target, optional active deployment source where enabled, OAuth authoring integration, GitLab-aware workflows, and merge-request authoring. |
| Forgejo | Self-hosted active deployment source where enabled, workflow source repository, copy target, and reviewable authoring path. |

Provider availability can depend on your plan, workspace configuration, and rollout state.

## Active source vs copy target

One repository is the active deployment source for a site. That source powers published docs, previews, and normal update checks.

Additional connected repositories can be used as copy targets. A copy target is useful for backup, provider testing, or migration rehearsal, but it does not become an automatic mirror and it does not power the live site unless you explicitly switch the deployment source.

When a GitLab or Forgejo repository is promoted from a secondary provider to the active deployment source, dubstack first copies the current docs files into that repository. If the copy fails, the previous active deployment source stays active.

Keep these states separate:

| State | What it means |
| --- | --- |
| Active deployment source | The repository and branch currently powering the site. |
| Repository copy target | A connected repository that can receive an on-demand copy of docs files. |
| Source repository | A code or product repository that workflows can read for context and use to draft documentation updates. |
| Authoring access | The provider permission path used to create branches, commits, pull requests, or merge requests in the docs repository. |

Source repositories are read-only context. They do not publish pages and they do not receive generated docs changes unless they are also the active docs repository.

## Choose a provider path

| Goal | Recommended path |
| --- | --- |
| Production docs from your own hosted GitHub repository | [GitHub](/deployment/github) |
| Keep a GitLab copy or prepare a migration | [GitLab](/deployment/gitlab) |
| Draft GitLab merge requests from agents or workflows | [GitLab](/deployment/gitlab) with OAuth authoring access |
| Publish from a self-hosted Forgejo docs repository | Configure Forgejo as the active deployment source in [Git settings](/deployment/git-settings) |
| Use a self-hosted Forgejo code repository for workflows | Add it as a source repository in [Git settings](/deployment/git-settings), then select it in [workflow configuration](/workflows/configuration). |
| Review generic provider concepts | This page |
| Configure an unsupported custom provider | Contact support or your dubstack operator before relying on it for production publishing. |

## Connect a repository

From the dashboard:

1. Open **Settings > Deployment > Git settings**.
2. Choose the provider.
3. Authorize the provider app, repository access token, or OAuth flow required by that provider.
4. Select the repository and branch.
5. Save the connection.
6. Run a manual update to verify the first sync.

If another provider was already active, wait for the initial repository copy to finish before treating the new provider as the production source.

## Repository requirements

A docs repository should include:

- MDX pages.
- `dubstack.json`.
- Images and assets referenced by pages.
- OpenAPI specs if the site has an API reference.
- Any reusable snippets used by pages.

## Branches and previews

Use the deployment branch for production docs. Use preview branches for review workflows when your plan and provider integration support previews.

Do not use preview branches as the long-term production source.

## Provider permissions

Grant the smallest provider scope that supports your intended workflow:

| Workflow | Permission needed |
| --- | --- |
| Read and publish docs | Repository read access. |
| Dashboard edits | Write access to content files and configuration. |
| Agent draft PRs | Branch and pull request creation access. |
| Webhook-driven updates | Webhook delivery from the provider. |
| Workflow source context | Read access to the selected source repository. |

For GitLab, repository read/copy access and authoring access are separate. The repository access token keeps the GitLab repository connection readable. GitLab OAuth authoring access lets workflows create branches, commits, and merge requests as an authorized GitLab user.

For Forgejo, the repository token must cover the source repository and the actions you want dubstack to perform. Read-only tokens can publish existing content. Authoring workflows need permission to create branches and pull requests.

## Source repositories for autodocs workflows

Autodocs workflows use source repositories as context when product implementation changes should produce documentation updates.

Use this pattern when:

- API or SDK code lives outside the docs repository
- a monorepo contains several services and only one path should influence a workflow
- a self-hosted Forgejo repository should remain internal source control while dubstack drafts docs changes in the connected docs repository

The workflow reads the selected source repository, applies the workflow prompt and path scope, then writes generated documentation changes to the active docs repository through the configured update mode.

For a safe first rollout:

1. Add the code repository as a source repository in Git settings.
2. Select a narrow path scope, such as `services/api` or `apps/marketing`.
3. Configure **Update from code changes** with **Require review**.
4. Merge a small source pull request or merge request.
5. Review the generated docs pull request before enabling broader coverage.

## First-sync troubleshooting

If the first sync fails:

- Confirm the repository is installed or authorized for the provider app.
- Confirm the selected branch exists.
- Confirm `dubstack.json` is present at the repository root.
- Confirm page slugs in navigation map to files.
- Re-run manual update after fixing provider access.

<Callout type="info">
  You can migrate between provider-backed sources, but keep one active production source at a time to avoid branch and publish confusion.
</Callout>
