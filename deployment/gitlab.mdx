GitLab support has two separate connections:

- a deployment token that lets dubstack read or copy repository content
- GitLab OAuth authoring access that lets workflows act as an authorized GitLab user

Developers can still use normal GitLab workflows. Clone the connected project, edit MDX files or `dubstack.json`, commit, push, and review changes through merge requests.

<Callout type="info">
  GitHub is the primary production deployment source in the default setup path. GitLab can be connected as a copy target and authoring integration today. GitLab production-source activation is workspace-controlled and should be verified in Git settings before switching a live site.
</Callout>

## What GitLab does today

| Capability | Status |
| --- | --- |
| Copy docs from the active deployment source into GitLab | Supported |
| Use GitLab as a backup or migration target | Supported |
| Connect GitLab OAuth for agent and workflow authoring | Supported |
| Create branches, commits, and merge requests from authorized workflows | Supported when GitLab OAuth is connected |
| Collect bounded merge request context for workflow runs | Supported when GitLab OAuth and repository context are connected |
| Use GitLab as the active production deployment source | Workspace-controlled; verify the dashboard shows it as the active deployment source |
| Self-hosted GitLab instance URL | Supported where the instance is reachable by dubstack |

## Deployment token versus OAuth

The deployment token and OAuth connection are intentionally different.

| Connection | What it is used for |
| --- | --- |
| GitLab deployment token | Reading repository files, validating branches, and keeping a GitLab copy target connected. |
| GitLab OAuth authoring access | Creating branches, commits, and merge requests from agent, Slack, and workflow authoring actions. |

Use both when you want GitLab-backed authoring. A deployment token alone can keep content connected, but authoring actions need OAuth so dubstack can act with an authorized GitLab user and respect the user's GitLab permissions.

## Which connection should you check?

Use the failing action to decide which GitLab credential to inspect.

| Failing action | Check |
| --- | --- |
| Manual update cannot read the repository | GitLab deployment token, project ID or path, instance URL, branch, and repository file permissions. |
| Copy docs into GitLab fails | GitLab deployment token, write permission for the target project, branch protection, and configured target branch. |
| Agent, Slack, or workflow cannot create a merge request | GitLab OAuth authoring access, connected user permissions, branch protection, and authoring readiness. |
| Workflow cannot read recent merge request context | GitLab OAuth authoring access and selected workflow repository context. |
| Pushes to GitLab do not update the live site | Whether GitLab is the active deployment source, whether webhooks are configured, and whether manual update succeeds. |

Do not rotate OAuth when a deployment token is expired, and do not rotate the deployment token when only authoring is missing. They unlock different paths.

## Connect GitLab as a copy target

1. Open the dashboard.
2. Go to **Settings > Deployment > Git settings**.
3. Choose **GitLab**.
4. Enter the GitLab instance URL. Leave it as `https://gitlab.com` for hosted GitLab.
5. Enter the numeric project ID or project path accepted by the dashboard.
6. Enter a GitLab deployment token.
7. Choose the branch.
8. Save the connection.
9. Copy docs from the active source into GitLab.

After saving, the dashboard should show GitLab as a configured copy target. If another provider is still active, GitLab is not serving production docs yet.

## Publish from a local checkout

Use this when GitLab is the active deployment source for the site.

```bash
git clone https://gitlab.com/your-group/your-docs-project.git
cd your-docs-project
git checkout -b docs/update-guide
git add .
git commit -m "docs: update guide"
git push -u origin docs/update-guide
```

Open a merge request and merge it into the configured deployment branch after review.

If GitLab is only configured as a copy target, pushes to GitLab do not publish the live site. The active deployment source still drives production updates.

See [Local Git workflow](/deployment/local-git-workflow) for the provider-neutral flow.

## Deployment token requirements

Use a GitLab project access token where possible.

Recommended token settings:

| Setting | Value |
| --- | --- |
| Role | Maintainer |
| Scopes | `api`, `read_api` |
| Expiration | Use your organization's rotation policy |

If project access tokens are unavailable, use a personal access token owned by a service account. Avoid using a personal employee token for long-running production workflows.

## Connect GitLab authoring access

GitLab OAuth is optional for read/copy workflows and required for GitLab authoring workflows.

Connect GitLab OAuth when agents, Slack requests, or scheduled workflows need to draft docs changes in GitLab.

To connect OAuth:

1. Open **Settings > Deployment > Git settings**.
2. Open the GitLab configuration.
3. Click **Connect GitLab** for hosted GitLab or **Connect Self-Hosted GitLab** for a reachable self-hosted instance.
4. Complete the GitLab authorization flow.
5. Return to Git settings and confirm the GitLab account is connected.

After OAuth is connected, eligible authoring actions can:

- create a feature branch
- write or update MDX files
- commit generated documentation changes
- open a merge request against the configured branch
- read bounded merge request context for workflow runs

<Callout type="warning">
  GitLab authoring is not enabled for hosted starter repositories or deployments protected from repository mutations. Connect a customer-owned GitLab repository before using GitLab merge-request authoring.
</Callout>

## Dashboard states

Use the status in Git settings to confirm which GitLab capability is available.

| Dashboard state | Meaning |
| --- | --- |
| GitLab copy target connected | The deployment token is valid and dubstack can copy docs into GitLab. |
| GitLab OAuth connected | Workflows can request GitLab authoring access when the connected user has project permissions. |
| Active deployment source | The site reads from GitLab for production docs. This state appears only when GitLab deployment-source activation is enabled for the workspace. |
| Copy docs available | GitLab is configured as a target and can receive a fresh copy from the current active source. |
| Authoring not ready | The deployment token may be connected, but OAuth, repository scope, or site eligibility is missing. |

## Active deployment source

GitLab active-source mode means the site reads its production docs from GitLab instead of treating GitLab as a copy target.

Before enabling it on a live site, confirm:

- the workspace has GitLab deployment-source activation enabled
- the GitLab project and branch are validated in Git settings
- a first manual update completes successfully
- the active source badge points at the GitLab repository
- your team understands which repository is now the source of truth

If active-source activation is not available in your workspace, continue using GitLab as a copy target and authoring integration.

## Copy behavior

When GitLab is configured as a copy target, dubstack copies the active docs source into the GitLab repository.

Use this for:

- backup copies
- migration testing
- validating GitLab repository structure
- preparing a future provider switch
- giving GitLab-based teams access to docs files

Keep one active production source at a time. Do not edit the source repository and GitLab copy target independently unless you are intentionally migrating.

## Update signals

GitLab copy-target mode does not make GitLab the live source. Pushes to the active deployment source continue to drive production updates.

When GitLab active-source mode is enabled, use the dashboard's manual update and provider validation controls to confirm the first sync before relying on GitLab updates for a production site.

## Authoring readiness

GitLab authoring is ready when all of these are true:

- the site has an active GitLab docs repository connection
- the repository is not a hosted fallback and the deployment is not protected from repository mutations
- GitLab OAuth authoring access is connected for the site or organization
- the connected GitLab user can read the project and create branches or merge requests
- the authoring model is enabled for the workspace

If GitLab authoring is not ready, dashboard workflows and Slack requests return a setup message instead of creating repository changes.

## Self-hosted GitLab

For self-hosted GitLab, the instance must be reachable by dubstack over HTTPS.

Before connecting:

- confirm the public base URL is correct
- confirm the project ID or path resolves through the GitLab API
- confirm the token can access the project
- confirm GitLab OAuth is configured if workflows need to write changes
- confirm outbound webhook/API traffic is allowed by your network policy

For the authoring OAuth setup path, see [Self-hosted GitLab OAuth](/deployment/gitlab-self-hosted-oauth).

## Troubleshooting

### GitLab token is rejected

Confirm the token has `api` and `read_api` scopes and can read the selected project.

### Initial copy did not complete

Check the active deployment source first. GitLab copy depends on a valid source repository and published docs files.

### GitLab cannot be selected as the active source

GitLab active-source activation is not enabled for the workspace. Use GitLab as a copy target and authoring integration, or contact your dubstack operator before switching a live deployment source.

### OAuth connects but copy still fails

OAuth and deployment tokens serve different purposes. Confirm the deployment token is still present and valid.

### Agent or Slack says GitLab authoring is not connected

Connect GitLab OAuth in Git settings. The deployment token is not enough for merge-request authoring because authoring actions need a user-scoped OAuth connection.

### Workflow context skips GitLab merge requests

Confirm the workflow has GitLab repository context selected, GitLab OAuth is connected, and the run type supports bounded merge request context. Scheduled runs and manual source-context runs can collect bounded merge request metadata when the connection is healthy.

### Self-hosted instance cannot connect

Confirm the instance URL is externally reachable and uses a trusted TLS certificate.
