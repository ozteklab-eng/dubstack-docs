Search helps readers find the right page without knowing your navigation structure.

dubstack builds search from published docs content. Good search quality starts with clear page metadata, strong headings, and navigation that reflects the way readers think about your product.

## Configure the search bar

Open **Settings > Deployment > Search** to change the placeholder shown in the public search entry points.

The dashboard saves this value to `search.prompt` in `dubstack.json` and mirrors it to the existing search widget placeholders for compatibility:

```json
{
  "search": {
    "prompt": "Search docs..."
  },
  "widgets": {
    "search": {
      "placeholder": "Search docs..."
    },
    "sidebar_search": {
      "placeholder": "Search docs..."
    }
  }
}
```

Use short helper text that matches the reader's intent. For example, API-heavy docs can use `Search endpoints...`, while internal knowledge bases can use `Search policies and runbooks...`.

<Callout type="info">
  Product and version filters are shown only after the site has indexed navigation metadata for those filters. If the dashboard marks those controls as unavailable, keep tuning search through page metadata, navigation labels, and ranking boosts.
</Callout>

## What search uses

Search quality is influenced by:

- page titles
- page descriptions
- headings
- body content
- navigation labels
- OpenAPI operation summaries and descriptions
- published page paths

Pages that are hidden from public indexing are not useful search candidates. Keep important pages visible in navigation and keep private content out of public docs.

## Tune page ranking

Use page frontmatter to tune search behavior when metadata and content structure are not enough.

```mdx
---
title: Quickstart
description: Create and publish your first docs site.
boost: 2
---
```

`boost` is a positive relevance multiplier. It affects in-site search, public MCP search, and assistant retrieval ranking. Use it for canonical pages that should rank highly for broad queries, such as quickstarts, migration guides, and API overview pages.

Keep boosts modest. Search should still return the most specific page for specific queries.

## Boost a navigation group

Set `boost` on a navigation group in `dubstack.json` to apply the multiplier to every page under that group.

```json
{
  "navigation": {
    "tabs": [
      {
        "tab": "Documentation",
        "groups": [
          {
            "group": "Getting started",
            "boost": 5,
            "pages": [
              "quickstart",
              "getting-started/create-site"
            ]
          }
        ]
      }
    ]
  }
}
```

A page inherits the boost from its nearest parent group. Nested groups can override parent boosts, and a page's own frontmatter `boost` always wins over inherited navigation boost.

Use group boosts for a small number of high-signal sections. Avoid boosting an entire docs site, because that removes the ranking signal.

## Exclude utility pages from search

Use `searchable: false` when a page should stay published and directly reachable but should not appear in search or public AI retrieval.

```mdx
---
title: Terms of service
description: Legal terms linked from the footer.
searchable: false
---
```

This keeps the page out of in-site search, public MCP search, the public MCP filesystem, and assistant retrieval indexes. It does not remove the page from navigation if you explicitly list it there.

Use `noindex: true` instead when the page should be excluded from sitemap and public indexing surfaces.

## Write searchable titles

Prefer titles that name the exact task or object.

| Weak | Strong |
| --- | --- |
| Overview | Authentication overview |
| Setup | Connect GitHub |
| API | API playground authentication |
| Settings | Configure deployment add-ons |

Generic titles are harder for readers and AI tools to interpret because the surrounding navigation context may not appear in every search surface.

## Write descriptions for snippets

Descriptions are reused across metadata, search snippets, AI indexes, and previews.

```mdx
---
title: Configure deployment add-ons
description: Enable page feedback, reader email collection, CI checks, preview authentication, and noindex controls.
---
```

Write descriptions as outcomes, not labels. A reader should understand why the page is relevant before opening it.

## Structure pages for retrieval

Use headings that match likely reader questions.

```mdx
## Connect a GitHub repository

## Trigger a manual update

## Troubleshoot failed syncs
```

Put examples near the explanation they support. Search and AI retrieval work better when the page keeps related concepts close together.

## Keep API search useful

For OpenAPI-backed pages, write clear operation summaries and descriptions in the spec.

```json
{
  "summary": "Create an API key",
  "description": "Creates a scoped API key for a deployment so workflow can call the dubstack API."
}
```

Avoid placeholder summaries such as `Get item` or `Post request`. API operation text becomes public docs content.

## Refresh search after changes

Search updates after content sync and publish completes.

If search results look stale:

1. Confirm the latest commit has synced.
2. Trigger a manual update from the dashboard.
3. Refresh the public docs page.
4. Search for exact words from the page title or heading.
5. Check whether the page is hidden, marked `noindex`, or marked `searchable: false`.
