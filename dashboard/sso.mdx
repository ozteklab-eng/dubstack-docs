Single sign-on lets Enterprise organizations route dashboard access through their identity provider.

<Callout type="info">
  SSO is an Enterprise feature activated through a sales-assisted agreement. Enterprise access is applied to the organization after its Stripe checkout is confirmed. It is not a self-service plan upgrade.
</Callout>

## What SSO controls

SSO controls how team members authenticate into the dubstack dashboard. It does not replace Git provider permissions, repository branch protection, or docs-site visitor authentication.

Use SSO when your organization needs:

- centralized identity management
- enforced company login methods
- easier offboarding
- enterprise access reviews
- separation between dashboard access and repository access

## Supported setup model

The dashboard stores SSO configuration at the organization level. Enterprise organizations can configure the provider details exposed by the Authentication settings page.

Prepare these values before configuring SSO:

| Value | Purpose |
| --- | --- |
| Connection name | A recognizable name for the workforce identity provider. |
| Discovery URL | The provider's OIDC discovery document, normally ending in `/.well-known/openid-configuration`. |
| Client ID | Public OIDC client identifier from the provider. |
| Client secret | Secret issued by the provider. Store it only in the dashboard field. |
| Scopes | OIDC scopes requested during sign-in. The default is `openid profile email`. |
| Login domain | A company email domain that must be verified before SSO enforcement. |

Exact field availability depends on the enabled provider and workspace entitlement.

## Verify a login domain

Domain verification proves that the organization controls the email domain used to route members into its SSO connection.

1. Add the company domain under **Verified login domains**.
2. Copy the generated TXT record name and content immediately. The content is shown only once.
3. In the DNS provider, create a TXT record using the displayed values. Leave TTL on **Auto** or the provider default.
4. Return to dubstack after DNS propagation and select **Verify**.

<Callout type="warning">
  Selecting **New value** invalidates the previous verification value. Update the DNS record before trying verification again.
</Callout>

DNS providers format record names differently. Cloudflare accepts the displayed host name. Other providers may append the domain automatically, so avoid entering the domain twice. Verification can remain pending while TXT changes propagate.

## SCIM provisioning status

SCIM provisioning is part of the Enterprise identity roadmap, but it is not currently a self-service dashboard flow.

Today, use SSO for sign-in control and manage team access from **Dashboard > Team members**. When SCIM is enabled for an Enterprise workspace, it should remain separate from sign-in configuration:

| Control | Purpose |
| --- | --- |
| SSO | Controls how members authenticate into the dashboard. |
| Team members | Controls current workspace membership and roles. |
| SCIM | Will provision, update, and deprovision members from an identity provider when enabled for the workspace. |

Until SCIM is enabled for your workspace, continue to remove users from both dubstack membership and connected systems during offboarding.

## Configure SSO

1. Open the dashboard.
2. Go to **Settings > Authentication**.
3. Confirm the organization has an active Enterprise agreement with SSO enabled.
4. Choose the provider type available for your workspace.
5. Copy the redirect URL shown by dubstack into your identity provider.
6. Enter the provider client and endpoint details in dubstack.
7. Save the configuration.
8. Test sign-in with a non-owner member before enforcing SSO operationally.

## Break-glass access

Keep at least one owner or admin account with a tested recovery path before changing identity settings.

Recommended practice:

- keep ownership on a durable company-controlled mailbox
- store recovery credentials in a password manager
- test SSO with a secondary member before relying on it
- document who can disable or repair SSO if the provider is unavailable

## Offboarding with SSO

Removing a user from the identity provider should stop future sign-ins through SSO, but you should also review:

- dubstack organization membership
- Git provider repository access
- Slack or Jira workspace access used by integrations
- pending invites
- active API keys the user created or managed
